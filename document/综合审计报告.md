## 2. 综合判定

总体方向可保留为：**持久化 Agent 工作流内核 + 按需工具上下文运行时**。`refract.md` 负责 Session/Turn、Intent 到 Action 的业务生命周期、注意力调度、证据/回执、文件与协作；HTML 资料提出 LCP 作为 MCP 之上的上下文平面，以四个北向入口承接工具发现、详情展开、批量执行和大结果读取。

该组合尚不能直接宣称状态机闭合、取消彻底、安全恢复、回执即真值、跨 Agent 安全组合或固定 Token 降幅。当前最重要的问题是跨模块的事实所有权、执行归属、预算结算、证据验证、取消和远程异步结果没有统一契约，而不是缺少更多模块。

建议先完成可恢复的单 Agent 只读内核和强基线，再引入写入、并行、协作、复杂贝叶斯、自动 Behavior 抽象和高级视图。安全控制、租户隔离、对象授权、基本审计、结果预算和 `unknown_outcome` 必须在最小闭环中存在，不能全部推迟到后期治理。

## 3. 正确的模块分层与所有权

### 3.1 逻辑分层

`refract.md` 的 L0–L8 是责任地图，不是严格串行的代码调用栈：

| 层 | 责任 | 必须避免的误读 |
| --- | --- | --- |
| L0 | 外部工具、知识、行为资源适配 | 目录或适配不等于授权和可信 |
| L0.5 | Workspace、文件、权限、快照、隔离、提交 | 不负责直接判定业务 Goal 达成 |
| L0.6 | Project 指令、架构、配置、约定 | 规则与事实必须有版本、来源和适用范围 |
| L0.7 | Tool/Skill/Protocol/Cognition/Behavior 治理 | 定义、版本、依赖和一次调用实例分开 |
| L0.8 | Profession 画像和验证偏好 | 角色与信任不能自动扩权 |
| L0.9 | Agent/Cooperation 身份、委托、拓扑、仲裁 | Registry 不应成为第二个万能调度器 |
| L1 | Session/Turn、六级生命周期、事件、预算、队列 | 作为业务状态唯一写入者 |
| L2 | 注意力对象、呈现元数据、版本引用 | 不是另一个事实库 |
| L3 | 路由、聚焦、切换、抑制、候选调度 | 输出建议；L1 最终确认 ready 和执行授权 |
| L4 | 当前模型请求的上下文编译 | 记录对象版本、预算、外置与截断 |
| L5 | 推理、规划、失败归因、命令提案 | 不能直接写成功状态、预算或权限 |
| L6 | 状态、契约、过程和业务终态验证 | 验证器自身要有版本和独立结果 |
| L7 | Evidence 依赖、融合、撤销和消费审计 | 向 L1 提交结论，不绕过命令端口改业务终态 |
| L8 | 验证轨迹沉淀为候选 | 必须经过留出集、影子/金丝雀和发布流程 |

### 3.2 LCP 的位置

LCP 不是替代 MCP 的新传输协议，而是模型与 MCP 服务之间的剖面加运行时：

```text
North / Model
  find_tools(query) → inspect_tool(id) → run(code, budget) → read_handle(id, cursor)
        ↓
Context Plane
  Manifest Store → Retriever → Budgeter → Executor → Shaper
                  Policy & Audit 横切所有入口和出口
        ↓
South / MCP
  server/discover → tools/list → tools/call
```

LCP 可以映射到 L0.7、L2、L3、L4、执行适配器和横切策略，但不能替代 L1 的业务生命周期、L6 的终态验收或 L7 的证据治理。四个入口恒定只约束模型可见入口 schema，不代表检索结果、`inspect`、代码、错误、句柄和历史的端到端成本恒定。

### 3.3 唯一事实所有者

| 事实 | 唯一所有者 | 其它模块的角色 |
| --- | --- | --- |
| Session/Turn/Intent/Workflow Task 状态 | L1 工作流内核 | 读取投影或提交命令，不重复写终态 |
| 能力定义和批准版本 | L0.7 Registry | Manifest Store 保存可失效的检索投影 |
| 候选和注意力次序 | L3 使用 Retriever | 只能产生建议，不能授予权限 |
| 上下文编码 | L4 使用 Shaper | 不修改原始 Observation |
| 权限 | 独立 PDP，Executor、Handle、File 等作为 PEP | Profession/信任只可收紧或排序 |
| 预算和配额 | 统一 Budget Ledger | LCP Budgeter 适配结果和执行限额 |
| 实际调用和沙箱 | Executor/连接器 | 记录原始结果、外部操作标识和未知结果 |
| 结构与业务验证 | L6 | 生成独立 VerificationRecord |
| Evidence 和结论依赖 | L7 | 管声明、来源、撤销和失效闭包 |
| 学习候选 | L8，再由 L0.7 注册激活 | 不直接替换正在运行的版本 |
| 协作委托 | L0.9 | L1 仍写 Task 状态，L3 仍消费调度建议 |

## 4. 核心执行数据流

### 4.1 交互与执行应分离

Session 是跨 Turn 的业务容器，Turn 是用户输入到响应的交互单元；Intent 只在 Turn.interpreting 捕获，Mission/Goal/Plan/Task 可跨 Turn，Action 不应被误解为必须随用户 Turn 结束。异步 Mission 的后台执行要求独立执行边界。

建议每个外部执行同时携带：

```text
ExecutionContext
  tenant_id, principal_id, agent_id, delegation_chain
  session_id, origin_turn_id, observed_in_turn_id?
  mission_id?, workflow_task_id?, action_id
  execution_id, operation_id, attempt_id, execution_span_id
  workspace_id?, snapshot_id?, capability_binding_id
  policy_version, authorization_context_id, approval_ref?
  budget_reservation_id, deadline, cancellation_epoch
```

`origin_turn_id` 表示触发来源，`observed_in_turn_id` 表示结果被哪一轮消费；`operation_id` 跨网络重试稳定，`attempt_id` 每次尝试唯一。Turn completed、Mission achieved、Attempt settled 是三个不同事件，不能相互推导。

### 4.2 可恢复执行闭环

```text
登记输入事件并去重
  → 创建/恢复 Session，恢复任务、预算、持久对象和未决执行
  → Turn received / interpreting，捕获或关联 Intent
  → 确认或承接 Intent，固定 Mission/Goal 验收契约
  → 生成 Plan 版本和 Task DAG，检查依赖、入口/出口、回退与预算
  → L3 选择候选注意力；L4 编译当前模型请求
  → find_tools 检索候选，先做权限/状态过滤
  → inspect_tool 固定完整 schema、版本和 digest
  → 预留预算、写入 intent-to-execute、生成 Action/Invocation
  → Executor 在 Policy/PEP 约束下执行南向 MCP/CLI/SDK
  → 每个有副作用的子调用保存 Observation、ReceiptCore 和 attempt
  → Shaper 以字段投影、分页、Handle 或受控摘要返回
  → L6 校验契约、过程和环境终态
  → L7 将有效 Observation/Verification 映射为声明级 Evidence
  → 仅在版本、租约、预算和证据闭包仍有效时提交 Task/Goal 状态
  → Turn 响应，结算实际成本并记录消费的证据/句柄
  → 更新 Session，重置非持久注意力；后台 Mission 继续使用保留预算
  → 恢复/关闭时对账 unknown outcome、释放租约、处理 dirty 现场和未决远程任务
```

事件重放只重建状态，不重新执行外部副作用。超时或断网而效果不明进入 `unknown_outcome`/`reconciling`，对账前不能普通重试非幂等写。

### 4.3 Receipt、Observation、Verification、Evidence

四者必须分开：

```text
Invocation/ActionAttempt
  → ObservationRecord（原始输出、产物、外部效果、版本）
  → ReceiptCore（谁、何时、执行什么、观察到什么、哈希/签名）
  → ReceiptIntegrityVerification
  → VerificationRecord（按版本化判据验证什么）
  → Evidence（支持/反驳哪个原子声明）
  → GoalAssessment / 业务终态
```

Receipt 证明执行事实和完整性，不自动证明业务正确；Evidence 绑定声明、来源、观察对象、判据、环境和失效条件；Goal 只能在独立验收契约通过后达成。不能让 Receipt 等待已验证 Evidence 才能锚定，又让 Evidence 等待 verified Receipt 才能创建，从而形成前置环。签名后的核心不可变，争议、撤销和补偿通过追加记录表示。

## 5. 生命周期和状态闭合问题

### 5.1 需要修订的状态

1. 取消传播引用 `Mission.cancelled` 和 `Plan.cancelled`，但两者原状态机未定义这些状态。不能用一条传播箭头隐式增加状态。
2. `Goal achieved` 的证据被撤销后，原状态机没有明确的失效/重开路径。建议保留“曾达成”的事实，另设 `validity=invalidated` 或 `verification_pending`，再启动纠正 Plan。
3. `Task completed` 的“所有 Action 成功”无法处理失败 attempt、可选 skipped、补偿调用和 unknown outcome。应按逻辑 Action 的必需效果和明确验收谓词判断，attempt 是执行尝试。
4. Plan DAG 无环不等于整个系统终止。retry、replan、MRTR、轮询、协商和代码循环都需要总次数、deadline、进展度量和死信责任者。
5. Session 的应用状态不能与 MCP 传输状态混为一谈。MCP 无状态请求不消除业务 Session、浏览器/数据库状态、句柄或远程任务状态。

### 5.2 取消、远程任务和未知结果

本地取消应采用：

```text
cancel_requested → draining → cancelled
                         ↘ completed_after_cancel
                         ↘ unknown_outcome
```

取消请求不等于远端已经停止，已提交的外部副作用也不能被网络取消撤回。MCP Tasks 2026-07-28 的外部核验显示：`tasks/cancel` 是合作式请求，ack 不保证停止，远程任务甚至可能最终 `completed`；`completed` 还可包含 `isError:true`。因此应区分：

- `WorkflowTask`：由 L1 验收业务目标。
- `RemoteTask`：保存南向 `taskId`、服务器身份、授权上下文、TTL、轮询状态、幂等键和最终原始结果。
- `Action/Attempt`：本地对远程调用或轮询的执行事实。

收到远程任务句柄只表示远程任务已创建，不表示 Action succeeded；轮询/通知可在前台 Turn 之外推进，但结果仍归属原 operation，并在用户下一轮消费时重新授权。旧 epoch 的迟到结果不能推进已取代的目标。`TaskHandle` 与 `DataHandle` 必须分型：前者保存远程执行状态、服务器身份、poll 间隔、TTL、取消和最终状态；后者保存结果所有权、来源 digest、权限投影、cursor 和数据 TTL。二者有不同生命周期与读取权限，不能用一个泛化 handle 字符串混用。MCP 的 `completed` 也不是业务成功：扩展允许 `completed` 携带 `isError:true`，而 `failed` 可表示协议层 JSON-RPC 错误，L1/L6 仍需检查业务结果。

## 6. LCP 契约与模块审计

### 6.1 Manifest

Manifest 是导航和版本固定信息，不是权限本身。至少要绑定服务器身份、工具 ID、版本、摘要、短签名、使用条件、禁止条件、风险/副作用、前置条件、schema digest、端点和策略范围。完整 schema 由 `inspect_tool` 按需展开。缓存键不能只有工具名，应包含租户、端点、版本、digest 和 policy scope；TTL 是缓存提示，不是授权期限。

### 6.2 Retriever

Retriever 负责候选和排序，Policy 负责硬授权。应支持词法/BM25、向量、签名/类型约束、状态和成本组合；低置信度可弃权、澄清或扩大检索。多工具任务要测完整所需工具集及其前置依赖召回，不只测单工具 top-k 准确率。暂时不满足登录/资源前置的工具不应被彻底隐藏，而应以安全原因和依赖暴露；真正禁止的工具必须不可见且不可执行。

近期多工具检索研究显示，多目标 completeness@k 可能显著低于单目标，且更高召回会增加调用和延迟；这些是具体数据集、模型和方法下的外部结果，不能直接当项目普遍上限。项目验收应记录 completeness@k、前置依赖召回、等价路径和扩大检索成本。

### 6.3 Budgeter

Budgeter 把软提示变成硬预算：输入/输出/总 Token、工具调用、重试、并行度、CPU、内存、墙钟、网络字节、存储、Handle 读取、MRTR 和轮询次数。超限应转 Handle、分页、受控摘要或明确错误，不能静默截断。

预算需要统一账本和原子 reserve/commit/release。跨 Turn Mission 不能同时挂在 Turn 子树和 Session 保留预算而重复计费；更稳妥的业务预算树为 `Session→Mission→Goal→Plan→Task→Attempt`，Turn 作为归因和临时窗口。任何时刻都必须满足：已结算消耗加有效预留不超过授权额度。

### 6.4 Executor

Executor 在隔离环境中执行类型化绑定或受控 CLI/SDK。默认无网络、无任意文件和环境变量读取，出站按域名/方法/端口/对象/数据分类约束，限制 CPU/内存/并发/子进程/墙钟/输出字节。`run` 是批量执行入口，不是一个天然原子 Action；每个有副作用的子调用都要继承 ExecutionContext、重新做 PEP 检查并生成独立 Invocation/Observation/Receipt。外层 Batch Receipt 只能汇总。

### 6.5 Shaper 与 Handle

优先采用服务端过滤/聚合、字段投影、分页和 Handle；紧凑编码需测解析、遗漏和端到端成功，模型摘要不能成为唯一真相。Handle 必须绑定 owner、tenant、Session、来源 Receipt/digest、数据分类、schema、TTL、权限投影、cursor、撤销 epoch 和审计引用，每次读取重新授权。分页若没有冻结结果集，应标注弱一致性；原始 Observation 被清理时，相关 Evidence 必须显式降低可复验等级。

### 6.6 Policy & Audit

Policy 是全入口和数据出口的强制闸门，不是末端日志。有效权限是用户授权、租户策略、委托链、Session、Task、数据对象和沙箱约束的交集。Profession 只能进一步收紧或改变排序，信任分不能授予新权限，Retriever 过滤不能代替 Executor、File、Handle 的最终强制检查。

跨 Agent 消息必须区分可信委托指令、不可信数据引用、provenance 和 authority scope。签名证明发送者和内容完整性，不会把外部数据提升为用户授权或可信指令。数据标签必须贯穿 Agent、Handle、摘要和最终写入，敏感出站需要明确目标和范围批准。

## 7. 文件、视图与注意力边界

Workspace/File 是工作现场锚点，不是 LCP 的隐含权限绕过。文件的 `unmounted → mounted → active → stale/dirty` 状态与 `read-only | writable` 访问模式正交；版本哈希、CAS、租约 fencing 和三方合并防止 TOCTOU。`stale` 不能作为当前真相消费；诊断性 metadata/diff 需与普通 read/write 区分。文件、Receipt、Evidence、Session/Turn 和 Cooperation 的锚点必须共同带版本和授权。

六种视图 ER/时序/流程/Venn/架构/脑图是关系投影，不是真相；渲染隐藏在模型上下文之外，约束交由 L6。脑图/associate 需要 visited 去重、深度/候选/预算上限；视图、摘要和索引都必须能追溯源版本。

注意力八操作分为：

- 强度：`focus` 提权，`blur` 降权但不删除。
- 驻留：`mount` 进入上下文且带预算/过期条件，`unmount` 离开但保留指针，`persist` 跨步骤/Turn 保留且有理由。
- 内容：`update` 随证据/变更传播刷新评分和摘要。
- 关系证据：`associate` 展开有界候选；`verify` 输出评估、证据和建议，不直接等同业务验证。

对象的驻留、优先级、新鲜度、保留范围和正文粒度应内部正交；`blur` 不等于 `unmount`，`persist` 不等于永久把正文塞入上下文。

## 8. 研究证据与声明边界

当前研究支持局部机制，不支持整个“L0–L8 + 六级生命周期 + 八操作 + 六视图 + 多拓扑协作”组合已经证明有效：

- Tool Attention 报告的 95% 定义 Token 降幅来自 120 工具合成模拟；任务成功率、费用和时延是投影，不能当生产端到端证据。
- GatewayBench 的安全/效用数字依赖模型、harness、噪声和一次运行条件；不能普遍外推。
- 多工具检索研究提示多目标 completeness@k、前置依赖召回和工具集合完整性比单工具 top-k 更关键。
- 格式整形研究表明 TOON/其它编码的收益依赖模型和任务，全链路可能因解析失败反增 Token；字段投影、摘要和可逆编码必须分开测。
- Lost in the Middle、LongMemEval、AgentFold、ACE 等研究支持对位置、长期记忆、增量摘要和原文可回取进行专项评估，但不证明固定“一两行摘要”或 70% 通用阈值。
- 多 Agent 研究显示任务可分解性、模型能力、协调方式和集中验证决定收益；签名、信任分和多 Agent 共识不自动证明统计独立或安全组合。

研究报告建议的强基线：B0 全量工具 + 简单 ReAct；B1 静态 toolsets/权限过滤；B2 BM25/混合检索 + 延迟 schema；B3 B2 + 字段投影/分页/Handle；B4 B3 + 代码编排；Oracle 只用于诊断上限。所有配置固定模型、权限、工具版本、初态、预算和独立终态判据。

核心指标必须分开报告：端到端成功率及置信区间、所需工具集合 completeness@k、前置依赖召回、输入/输出/缓存/推理 Token、总任务费用、p50/p95/p99 时延、重试和未知结果、校准误差、覆盖/弃权率、攻击成功率、越权/外泄、取消残留、重复副作用和恢复等价率。Token 降幅不是架构成立的充分条件。

## 9. P0/P1 风险与实施门槛

### P0：发布前必须闭合

1. Receipt/Evidence/Verification 前置环：建立不可变 Invocation/Observation/ReceiptCore，再独立完整性验证、业务验证和声明证据。
2. LCP `run` 子调用治理：ExecutionBatch、每子调用 Action/Attempt、Policy/预算/幂等/回执和外部效果。
3. 外部副作用未知结果：operation/attempt、幂等键、`unknown_outcome`、reconciling、查询或人工核对；不得普遍承诺 exactly-once。
4. 取消语义：`cancel_requested/draining/cancelled` 加 completed-after-cancel/unknown，旧 epoch 不得提交；RemoteTask 与 WorkflowTask 分离。
5. 租户/授权贯穿缓存、Manifest、Handle、Receipt、委托、恢复和每次子调用。
6. 写操作前置的 PDP/PEP、审计和最小权限；Policy 不能晚于代码执行。
7. 文件提交 CAS、fencing、dirty 草稿保护和因果回滚；本地快照不撤销远程邮件/支付/删除。
8. 跨 Agent provenance/taint：可信指令与不可信数据通道分离，不能由签名自动升格权威。

### P1：功能扩展前必须验证

- Mission/Plan 取消状态、Goal 证据撤销回退、Task skipped/failed attempt/unknown 的完成谓词。
- Session/Turn 澄清续接、异步执行归属、预算 reserve/transfer/settle 和清理保留额。
- Retriever 多工具完整召回、暂时不可执行前置原因、associate/脑图循环和扩大召回。
- 视图/摘要/Handle 的版本、新鲜度、分页一致性和原文保留。
- L1/L3 调度器、L6/L7 验证/仲裁器、Policy/Budgeter 的唯一写入与端口边界。
- 循环、replan、MRTR、轮询、协商、锁和撤销传播的次数、deadline、进展与死信。

## 10. 路线和验收

### 10.1 Agent 工作流路线

1. **只读串行内核**：单 Agent、最小 Session/Turn、少量工具、只读 Workspace、Receipt/Verification/Evidence 分离、统一预算和最小注意力调度。
2. **写入与恢复**：Task DAG、attempt/unknown、文件 CAS、取消栅栏、证据撤销、快照对账、Session/Turn 恢复。
3. **双 Agent 与批量执行**：Task 级委派、隔离 Workspace、ExecutionBatch 子调用审计、合并点和 fencing。
4. **适应性调度与学习**：候选评分、增量经验、影子/金丝雀、任务族校准、未见任务测试。
5. **按需扩展**：多拓扑、高级视图、复杂贝叶斯和大规模证据治理，仅在基线显示净收益后启用。

### 10.2 LCP 路线

1. **P0 计量与基线**：定义/结果/往返/协议成本，按请求、Task、Turn、Session 和租户归因。
2. **P1 代理 MVP**：Manifest 缓存、混合检索、权限/状态门控、结果整形和 Handle。
3. **P2 代码模式**：高频类型化 binding、沙箱、出站白名单、子调用 Receipt 和资源限额。
4. **P3 契约与治理**：Manifest/Budget/Handle 扩展、签名、撤销、审批、审计和策略迁移。

两条路线是不同维度，不能把 HTML 的周数或性能目标直接当项目保证。安全、租户、授权、基本审计和 unknown outcome 要前移到最小可用闭环。

### 10.3 故障验收

至少注入并通过以下场景：远端写成功后本地崩溃；取消后远端仍完成；`run` 第三步失败但前两步已产生副作用；租户 A/B 访问同一端点和可猜 Handle；权限撤销/锁过期/外部文件变更；Goal 证据撤销；MRTR/input_required 重复或拒绝；分页期间数据变化；worker 迟到和乱序；最后额度并发预留；Session 关闭时 dirty buffer 和 unknown attempt 未决。

每项报告：任务效用、独立终态、攻击成功率/越权率、未知结果比例、取消残留、重复副作用、恢复后的预算差额、p95/p99 时延、总费用及可复验性。

## 11. 最终结论

应保留的架构骨架是：Session/Turn 与业务生命周期分离、Plan/Task DAG、按需工具上下文、版本化 Workspace、视图投影、不可变执行事实、声明级证据和统一委派协议。第一优先级不是增加更多概念，而是确定唯一事实所有者并闭合：状态迁移、ExecutionContext、Invocation/Observation/Verification/ReceiptCore、PDP/PEP、预算账本、幂等/未知结果、取消/远程任务、文件提交和 provenance。

在这些不变量通过属性测试、故障注入、固定测试集和独立终态评测前，不应宣称“取消彻底”“可安全重放”“回执即真值”“四入口成本恒定”或“多 Agent 自动安全”。通过后再逐个消融验证脑图、Profession、贝叶斯、Behavior、协作拓扑和代码执行是否带来净收益。
