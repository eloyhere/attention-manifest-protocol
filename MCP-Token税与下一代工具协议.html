MCP 的Token 税

模型还没开始干活，超过四分之一的上下文就已经被工具说明书吃掉了。这不是某一个服务器的 bug，而是“把一切能力都塞进提示词”这条路线的结构性成本。本报告拆解这笔账，并回答一个问题：下一个工具协议，应该长什么样。

00 / SUMMARY

结论先行如果只看一页，看这五条。

核心判断

MCP 的问题不在“协议编码”，而在“上下文装配策略”。因此，推倒重写一个新协议，收益极低；重新设计工具与模型之间的“上下文平面”，收益极高。后者的工程量小一个量级，且不必赢下网络效应。

  • 成本有四类，优先级截然不同

    定义税（每轮固定）、结果税（随轮次二次增长）、往返税（每步一次推理）、协议税（握手与状态）。在数据密集型任务里，结果税最贵，却最少被讨论；定义税最显眼，所以被过度优化。

  • 2026 年的答案已经收敛为三个动作

    推迟（defer）：工具定义按需加载；外置（externalize）：执行搬进沙箱，中间结果不回上下文；压缩（compress）：结果换一种编码、换一个粒度。三者可叠加，不互斥。

  • 最强证据来自“不改协议”的方案

    Anthropic 的工具检索在 API 侧把 72K 降到 8.7K（−85%），准确率反升 25 个百分点；Cloudflare 的 Code Mode 用约 1,000 tokens 覆盖 2,594 个端点。两者都没有修改 MCP 的线上格式。

  • “新协议”唯一可行的形态是剖面（profile）

    南向继续讲 MCP（36,134 条 registry 条目、13,087 个可用端点），北向只对模型暴露 3–5 个元工具加一份签名清单。把创新放在运行时，而不是替换插座。

  • 先做计量，再做优化

    没有 per-server / per-turn 的 token 账本，任何“省 token”的结论都是猜测。建议把“每轮工具预算”做成产品的一等公民，而不是事后调参。

    01 / BACKGROUND

    “AI 的 USB-C”，插满了会短路MCP 用两年时间解决了 N×M 的集成问题，也顺手把集成成本搬进了上下文窗口。

    2024 年 11 月，Anthropic 发布 Model Context Protocol，用 JSON-RPC 统一了模型与外部工具、数据源的连接方式。这个类比很成功：MCP 是 USB-C，任何客户端插上任何服务器都能用。到 2026 年 9 月，官方 registry 已收录 36,134 条服务器条目、22,151 个远程端点。

    但 USB-C 的类比漏掉了一件事：现实里的 USB-C 插上就能用，而 MCP 每插一个设备，都必须把该设备的完整说明书——每个工具的名字、描述、JSON Schema、枚举、嵌套对象——抄进模型的提示词里。插十个设备，就抄十份说明书。这些说明书在每一轮对话中都要重新计费、重新占用注意力。

    工具不是免费的。每一个工具定义都是一段永久驻留的提示词，而提示词的长度，就是模型注意力的税率。 — 本报告的核心观察

    三场同时发生的爆炸

    单独看，任何一场爆炸都可控；三者叠加，才让 2026 年的 Agent 陷入“工具越多、表现越差”的困境。

    EXPLOSION 01

    工具数量爆炸

    一个 GitHub 服务器就有近百个工具；Jira 一家约 17K tokens；企业内部动辄数十个 SaaS、数百个 API。工具从“几个函数”变成“一个应用商店”。

    后果：定义税从数百 token 涨到数万 token。
    EXPLOSION 02

    结果体积爆炸

    工具返回的不再是状态码，而是日志、表格、代码库检索结果、PDF 解析文本。一次调用返回 200KB 原始数据是常态，而模型真正需要的往往只是 1KB 的聚合结论。

    后果：结果税随任务轮次二次增长。
    EXPLOSION 03

    任务步数爆炸

    Agent 从“一问一答”变成 20–50 步的循环。每一步都是一次完整推理，都要重放此前全部上下文。20 次工具调用意味着 20 次推理，而非 1 次。

    后果：往返税与时延线性叠加。

    繁荣的另一面： registry 的真实质量

    2026 年 9 月，Council of AI 对官方 registry 与 Docker 目录做了一次全量探测：22,196 个远程端点中，只有 13,087 个真正以 MCP 协议应答；4,948 个要求认证，1,411 个应答但根本不是 MCP，1,259 个不可达。更值得警惕的是“自述一致性”——在 5,828 个可比对端点中，47.4% 至少有一个维度自相矛盾（版本号最常见，其次是工具列表）。

    另一个维度是“用得多深”。Stacklok 与 AAIF 在 2026 年中的一项调查（100 名工程师）显示：41% 的软件组织声称 MCP 已进入生产，但 86% 的使用仍停留在实验或本地阶段，只有 5% 在企业范围内被治理，49% 把安全列为首要阻碍。这与“MCP 已死”的论调恰好相反——它不是没人用，而是用得很浅、管得很松。

    这意味着什么

    “工具很多”并不等于“能力很强”。当近半数服务器的自述与行为不一致时，客户端为了容错，只能倾向于多加载、多暴露、多重试——每一个容错动作，最终都会变成 token。生态的碎片化，才是 token 浪费的上游原因。

    02 / COST

    四类 Token 成本，和一张被算错的账大多数团队只盯着“工具定义”，却忽略了真正会复利的那一项。

    把一次 Agent 任务的账单拆开，会看到四种性质完全不同的成本。它们的最优解法互相冲突，因此必须分开度量、分别优化。

    TAX 01 · FIXED, PER TURN

    定义税：每轮都要重交的“说明书费”

    所有已连接服务器的工具 schema，在每一轮推理前被序列化进系统提示。它是固定成本：无论这轮是否用到，都要付费；也是缓存友好的：只要工具集不变，prompt cache 可以摊薄。

    口径：五服务器 58 工具 ≈55K（Anthropic）；GitHub 单服务器 2025-08 估算 93 工具 ≈55K，2026-08 复测为 85 工具 26.6K、默认 44 工具 14.2K；Anthropic 内部峰值 134K。
    TAX 02 · VARIABLE, QUADRATIC

    结果税：会复利的“数据搬运费”

    工具返回的原始 JSON 进入上下文后，不会被自动遗忘。第 3 轮取回的 200KB 日志，在第 4、5、6…轮仍要重放。N 步任务的结果成本约为 O(N²)，这是最被低估的一项。

    实测：某预算核查任务，2,000+ 条明细（50KB+）全部入上下文；改用代码编排后仅回传 1KB。
    TAX 03 · LATENCY

    往返税：每一步都要“重新思考一遍”

    自然语言工具调用要求每次调用都回到模型：读结果、判断、再决策。20 次调用 = 20 次推理，每次都要处理整个上下文。它主要不烧钱，烧的是时延与错误率——每次往返都是一次新的出错机会。

    实测：代码编排 20+ 次调用可省去 19 次推理往返。
    TAX 04 · PROTOCOL

    协议税：握手、会话与“不该存在的状态”

    initialize 握手、Mcp-Session-Id、SSE 重连、能力协商——单个请求的开销不大，但它们让缓存失效、让水平扩展变难、让“无状态重试”变得昂贵。2026-07-28 版规范把它们删了，恰好证明这部分是历史包袱。

    变化：新规范改为无状态请求 + server/discover + 可缓存列表（ttlMs）。

    为什么“结果税”比“定义税”更致命

    定义税是线性的：第 N 轮付 N 次同样的钱，可以用 prompt cache 打到一折。结果税是二次的：每一轮新增的结果，都会在后续所有轮次中被重复计费。以 55K 定义、每轮 10K 结果、20 轮为例：定义累计约 1.1M，结果累计约 2.1M，第 11 轮起结果反超；若单次结果 50K（约一份 200KB 文档），结果累计 10.5M，是定义的 9.5 倍。优化顺序因此应当是：先结果，后定义，再往返。

    03 / MECHANISM

    为什么“更多上下文”会让模型更笨不是玄学，是注意力预算、检索干扰与错误恢复三件事的叠加。

    Token 只是账单的外显。真正让 Agent 变差的，是上下文变长之后，模型对“该看什么”失去了分辨率。

    3.1 注意力是稀缺资源，不是免费容量

    Transformer 的注意力计算随序列长度平方增长，但更关键的是有效注意力被稀释：当上下文中混入大量与当前子目标无关的工具描述和历史结果时，模型对关键信息的召回率下降。业界把这一现象称为“context rot”（上下文腐化），并观察到当上下文利用率超过约 70% 后，推理质量出现非线性下滑——这个阈值来自一线工程经验，不同模型有差异，但方向一致。

    Chroma 在 2025 年 7 月对 18 个模型做过一组对照实验：即使任务本身很简单，输入变长也会让表现下降；加入一个干扰项就有影响，四个干扰项叠加更明显；一段约 300 tokens 的聚焦提示，可以打赢 113K tokens 的全量提示。

    这解释了一个反直觉的现象：把窗口从 200K 扩到 1M，并不能让 Agent 变强。窗口越大，注入的无关内容越多，信噪比反而越低；而成本按时长线性上涨。

    3.2 工具越多，选错的概率越高

    工具选择是一个“在 N 个相似选项中做区分”的任务。当工具名高度相似时——比如 notification-send-user 与 notification-send-channel——模型必须在描述文本里找到那个决定性的差异词。工具越多、描述越长，这个差异词越容易被淹没。选错的代价不只是浪费一次调用：它会触发重试、澄清、回滚，每一次都是额外的推理轮次与上下文污染。

    因此，token 效率与任务成功率不是 trade-off

    Anthropic 的公开数据显示，开启工具检索后，Opus 4 在 MCP 评测上的准确率从 49% 提升到 74%，Opus 4.5 从 79.5% 提升到 88.1%——上下文更短，判断更准。这打破了“省 token 必然牺牲效果”的直觉：在工具过载区间，二者是同向的。

    3.3 三个杠杆：推迟、外置、压缩

    所有有效的优化，最终都落在三个动作上。它们的组合，构成了下一代工具协议的全部设计空间。

    LEVER 01

    推迟 Defer

    不在第一轮加载全部定义。先给模型一份“目录摘要”，需要时再检索、展开完整 schema。本质是把“预加载”换成“按需分页”。

    省的是：定义税
    LEVER 02

    外置 Externalize

    把编排逻辑与数据处理搬进沙箱。工具变成代码里的函数，中间结果留在沙箱，只有最终结论回到模型。本质是把“对话式调用”换成“程序式调用”。

    省的是：结果税 + 往返税
    LEVER 03

    压缩 Compress

    改变结果的编码与粒度：结构化数组用更紧凑的格式、大结果转句柄按需切片、超长文本先摘要再入上下文。本质是提高“每 token 的信息密度”。

    省的是：结果税

    三个杠杆的工程属性完全不同：推迟是检索问题（召回率决定成败），外置是安全与运行时问题（沙箱隔离决定可行性），压缩是格式与信息论问题（可逆性决定风险）。把它们混为一谈，是大多数方案失败的起点。

    优化的目标不是“用最少的 token”，而是在给定任务成功率下，找到上下文成本的最小值。这是一个帕累托前沿，不是一个单点。 — 设计原则
    04 / LANDSCAPE

    2026 前沿图谱：五种范式已经成型过去 12 个月，行业没有发明新编码，而是把“什么时候给模型看什么”重新设计了一遍。

    下面这条时间线只收录对“上下文成本”有实质影响的事件。可以看到一个清晰的转向：2025 年大家在优化单次调用的格式，2026 年转向优化整个会话的信息流。

    2025-09

    Cloudflare 发布 Code Mode

    把 2,594 个 API 端点折叠成三个入口（search / execute / docs），模型写 TypeScript 在 isolate 中调用。全量 API 描述从约 117 万 tokens 降到约 1,000 tokens。

    2025-10

    Agent Skills：渐进披露进入“知识层”

    把技能写成文件，元数据（约 100 tokens）常驻，正文按需加载。它证明了“分层加载”不只适用于工具，也适用于说明书本身。

    2025-11-04

    Anthropic《Code execution with MCP》

    把 MCP 服务器暴露为文件树中的 TypeScript 模块，模型 import 后调用。示例工作流从 150K 降到 2K（−98.7%），并顺带把敏感数据留在沙箱内。

    2025-11

    Tool Search / Programmatic Tool Calling / Tool Use Examples

    三件套同时发布：检索式加载、代码内编排、以示例替代冗长描述。定义 72K→8.7K，准确率 49%→74%；PTC 让复杂研究任务 token 降 37%。

    2025-11-25

    MCP 规范： tasks 进入实验阶段

    长任务可以轮询取结果，不必阻塞等待；同时引入 URL 模式 elicitation、OAuth Client ID Metadata Documents。协议开始为“长时运行”做准备。

    2025-12

    MCP 转入 Linux Foundation 旗下的 Agentic AI Foundation

    治理中立化，与 goose、AGENTS.md 等一同托管。协议从此不再由单一厂商单方面定义，但路线图也更难激进。

    2026-04

    “Tool Attention”论文：把门控做成中间件

    用句向量算意图-工具重叠度，叠加状态门控与两阶段懒加载，在 120 工具模拟中把每轮 47.3K 降到 2.4K（−95%），上下文利用率 24%→91%。作者明确标注：端到端指标为投影，非线上实测。

    2026-07-28

    MCP 规范大改：删会话、去握手、加缓存

    移除 initialize 与 Mcp-Session-Id，改为无状态请求；新增 server/discover；列表结果必须带 ttlMs 与 cacheScope；要求 tools/list 稳定排序以提升 prompt cache 命中；tasks 移出核心成为官方扩展。

    2026-09

    生态体检：三万条条目，一半自述对不上

    registry 达 36,134 条；实测 59% 端点可用、47.4% 至少一处自相矛盾。同期安全社区披露“运行时门控的元数据投毒”攻击（Deadbugz），把“工具描述可变”变成供应链问题。

    2026-10

    优化下沉到框架：FastMCP 4 内置 Code Mode 与 Tool Search

    两个能力从“论文/博客”变成服务器框架的标准变换（transform），意味着中小团队不必自研网关也能享受大部分收益。

    五种范式，与它们各自省下的那一项

    范式代表实现机制主要省哪类结构性代价
    全量注入多数 MCP 客户端默认行为启动即序列化全部 schema—定义税随服务器数量线性上涨，无上限
    检索式加载Anthropic Tool Search；FastMCP Tool Search元工具 + 关键词/BM25/向量检索，命中后展开 schema定义税多一次检索与推理；召回率决定上限
    网关门控Tool Attention；Docker MCP Gateway；企业自建 broker中间件按意图、权限、状态筛选 top-k 工具定义税单点故障；多租户权限模型复杂
    代码执行Cloudflare Code Mode；Anthropic PTC；mcp-pyrunner工具变函数，编排在沙箱内完成，只回传结果定义 + 结果 + 往返沙箱安全、可观测性、代码生成错误
    输出整形TOON；分页游标；结果句柄；服务端摘要改变编码、粒度与引用方式结果税格式兼容性；信息损失不可逆

    五种范式可叠加。生产系统通常是“网关门控 + 检索式加载 + 输出整形”，代码执行作为高价值路径的可选加速器。

    协议层已经做了减法，但没有解决经济学

    2026-07-28 版规范是一次“去状态化”重构。它对工程质量的提升是实打实的，但对 token 账单的直接贡献有限——因为账单的大头在客户端如何装配上下文，而不在线上传了什么。

    规范变化做了什么对成本的真实影响
    无状态化删除 initialize 握手与 Mcp-Session-Id，版本与能力随每个请求放在 _meta重试/扩缩容更便宜；对 token 几乎无影响，但降低了“为保会话而保上下文”的诱惑
    server/discover服务器必须实现该 RPC，声明版本、能力与身份客户端可在加载前做一次廉价探测，为“先目录、后详情”提供协议依据
    可缓存列表tools/list 等结果必须带 ttlMs 与 cacheScope减少重复拉取与轮询；让“清单缓存”成为标准行为而非客户端私货
    稳定排序服务器应以确定顺序返回工具列表直接提升 prompt cache 命中率，这是最被低估的一条
    MRTR服务端索取输入改为返回 input_required，客户端重试原请求减少 server-initiated 请求的复杂状态机，降低失败重试成本
    tasks 转扩展长任务从核心移入 io.modelcontextprotocol/tasks，改为轮询避免长阻塞连接；但轮询本身会产生额外请求，需要退避策略
    弃用 roots/sampling/logging三类能力进入弃用窗口减少“服务器反向调用模型”的隐性成本与安全面

    来源：MCP Specification 2026-07-28 “Key Changes”（SEP-2567 / 2575 / 2322 / 2549 / 2663 / 2577）。

    一个正在分叉的共识

    协议层 2026 年的工作，优化的是可缓存性（稳定排序、ttl、无状态），因为提示词缓存的命中率比“少几百 token”更决定真实账单；而多数厂商与论文仍在优化token 数量。两者并不等价：一份更短但每轮都变的目录，可能比一份更长但完全命中的目录更贵。更麻烦的是，唯一一项独立评测发现，纯靠“换编码”压缩会带来准确率损失（见第 05 节 TOON 条目）。这是本报告认为最值得下注的判断：稳定性 > 压缩率。

    05 / SIGNALS

    八个还没被广泛抄走的亮点它们未必最出名，但每一个都指向了可复用的设计模式，而不是一次性的技巧。

    以下按“可复用性”而非热度排序。每张卡片只回答三件事：它做了什么、证据是什么、我们能拿走什么。

    01 · SERVER-SIDE TRANSFORM

    FastMCP 4 的 Code Mode / Tool Search 变换

    把两种优化做成服务器框架的“变换层”：开启后，服务端自动把工具集折叠成一个代码执行入口，或挂上检索入口。业务代码几乎不改。

    可拿走：优化应该是可开关的中间层，而不是重写服务器。这决定了它能否被大范围采用。
    已发布 v4.0.5框架层
    02 · DEFERRED LOADING

    Anthropic 的 defer_loading 与 mcp_toolset

    在 API 层给工具打“延迟加载”标记：整个服务器可默认不加载，只把最常用的 1–2 个工具常驻。defer_loading 的工具不进入初始 prompt，因此不破坏 prompt cache。

    可拿走：延迟加载的正确姿势是“从初始 prompt 中彻底移除”，而不是“先放进去再让模型忽略”。
    生产可用72K→8.7K
    03 · SANDBOX EXECUTION

    Cloudflare Code Mode 的 isolate 执行器

    每个会话一个 Dynamic Worker isolate，模型生成的 TypeScript 在其中运行，通过类型化绑定调用 API。工具描述只剩 search 与 execute 两个。

    可拿走：“一个执行工具”比“一千个工具”更省，但前提是沙箱足够便宜、足够隔离、启动足够快。
    2,594 endpoints≈1K tokens
    04 · MIDDLEWARE GATING

    Tool Attention：把“注意力”变成可计算的分数

    用句向量计算用户意图与工具描述的重叠度（ISO 分数），叠加状态门控（前置条件、权限范围），再做两阶段懒加载：上下文里只留摘要池，top-k 才展开完整 schema。

    可拿走：检索不该只按“语义相似”，还要按状态可用性过滤——没登录的工具不该被召回。
    arXiv 2604.21816模拟 −95%
    05 · CATALOG ENCODING

    TERSE Tool Catalog：给“目录”本身设计编码

    不是在调用时压缩，而是在目录层定义一种更紧凑的工具清单表示：短标识、分层命名、可增量拉取。10 个真实工具定义从 1,948 压到 650 tokens（−66.6%），还额外塞进了 WHEN / ERR / TAGS 三个字段。

    可拿走：大多数方案优化了 schema，却忘了“目录”才是每轮都要出现的东西。目录应是可缓存、可分页、可签名的。
    扩展规范草案−66.6%+8.3pp 选择准确率
    06 · OUTPUT ENCODING

    TOON：为 token 而不是为解析器设计序列化

    面向“同构对象数组”的紧凑文本格式，用一次表头 + 行式数据替代重复键名，宣称比 JSON 少三到六成。但 2026 年一项独立评测（4 个 agentic benchmark × 5 个开源模型）只测到 ≤18% 的节省，且伴随约 9 个百分点的准确率损失，多轮解析还会级联失败。

    可拿走：换输出格式仍是投入产出比最高的一招，但必须用任务成功率验收，而不是只看 token 计数。
    约 −40%（厂商）独立评测：−18% / −9pp
    07 · REPRESENTATION

    Playwright MCP：用无障碍树替代截图

    浏览器自动化不走“截图 + 视觉模型”，而是把页面的 accessibility tree 转成结构化文本。同样的操作，视觉 token 被换成了可定位的节点引用。

    可拿走：省 token 的最高境界是换表示，而不是压缩表示。选对模态，成本差一个数量级。
    微软维护高采用
    08 · ANTI-PROTOCOL

    gh CLI：零定义成本的“反向 benchmark”

    编码 Agent 本来就会用 gh、git、curl。给它们一个终端，等于给了数百个“预训练过的工具”，定义成本接近于零，还能用 --help 自解释。

    可拿走：如果一件事已有成熟 CLI，包一层 MCP 往往是负优化。新协议必须回答：凭什么比 shell 更好？
    范式挑战零 schema
    SEP-2640 · SKILLS

    把“说明书”也变成按需资源

    技能以 skill:// 资源暴露，列表只返回 frontmatter 与摘要；规范明确要求宿主“不得在连接、列举或审批时提前抓取技能正文”。这是渐进披露第一次被写进协议文本。

    SEP-1865 · MCP APPS

    UI 也是一种 token 优化

    交互结果渲染为应用资源，仅服务于该应用的内部工具不会进入模型的工具列表。把“多轮文本往返”换成“一次渲染”，省下的是往返税。

    JEVSEARCH · EXPERIMENTAL

    检索不出来时，允许“没有”

    用校准过的 yes/no 概率决定是否返回结果，无匹配时返回空，而不是硬塞一个“最不差”的工具。对漏召回导致的误调用，这是一个反直觉但有效的补丁。

    把八个作品放在一起看

    它们没有一个在改 JSON-RPC 的字段。真正的创新集中在三处：目录与详情的分离（01/02/05）、执行位置的下沉（03/04）、结果表示的重选（06/07）。第八个则提醒我们：有时最优解是退出协议。

    06 / WHAT WORKS

    成功样例：它们都不是“工具更多”，而是“面更小”六个已上线、可验证的案例，以及它们共同的技术选择。

    一个反直觉的规律：真正被大量使用的 MCP 服务，工具数量通常很少（3–15 个），场景极窄，但在那个场景里做到了“不用看文档也会用”。

    CASE 01 · CLOUDFLARE

    把 2,594 个端点折成 3 个入口

    远程 MCP 服务器托管在边缘，OAuth 复用现有账号体系；Code Mode 只暴露 search、execute 与 docs 三个入口，模型写 TypeScript 调用全部 API。

    结果：2,594 个 API 端点，原生逐端点 schema 约 117 万 tokens，折叠后约 1,000 tokens——三个数量级。

    关键选择：不为 Agent 单独造 API，而是给现有 API 生成类型化 SDK，再把 SDK 塞进沙箱。
    CASE 02 · ANTHROPIC

    把“检索”做进模型 API 本身

    Tool Search 让 defer_loading 的工具完全不进入初始 prompt；PTC 让工具在代码沙箱里被调用。Claude 的 75+ 连接器都建立在 MCP 之上，而这两项能力是让它们规模化可用的关键。Claude Code / Agent SDK 已默认开启工具检索：每次最多加载 5 个工具，目录上限 1 万。

    结果：定义 72K→8.7K；50 个工具的成本被压到 10–20K tokens；官方称工具数超过 30–50 个后选择准确率开始下降。

    关键选择：优化发生在客户端/API 层，服务器完全无感——这是覆盖面最大的杠杆。
    CASE 03 · PLAYWRIGHT MCP

    用无障碍树替代截图

    微软维护的浏览器自动化服务器，把页面表示为可定位的 accessibility tree 节点，而不是像素。模型看到的是“按钮 #12，名字=提交”，不是一张 1280×800 的图。仓库 38,466 星。

    结果：成为编码 Agent 的事实标准浏览器工具；同样的操作，token 成本比视觉方案低一个数量级。

    反讽：其 README 如今明确建议，编码类 Agent 优先用 CLI + Skills，仅在需要有状态、迭代式交互时才用 MCP。最成功的 MCP 服务器，自己在劝你少用 MCP。
    CASE 04 · CONTEXT7

    把“文档”做成按需检索，而不是塞进 prompt

    面向第三方库的文档服务器：先按库名与版本解析，再按问题检索片段，只回传命中的几段，而不是整本 docs。63,423 星。

    结果：被主流编码工具广泛集成，显著降低“API 幻觉”——模型不再编造不存在的函数签名。

    关键选择：版本化 + 片段化。文档类工具的价值在“精确”，不在“全”。
    CASE 05 · LINEAR / FIGMA

    把“权限分级”做成产品功能

    Linear 的远程服务器跑在 mcp.linear.app/mcp，OAuth 2.1 + 动态客户端注册，单独提供只读端点与只读 scope，并支持 Okta 企业级托管授权。Figma 托管 mcp.figma.com/mcp，列出 25+ 客户端，画布写入仍在 beta。

    结果：两者都不是“万能入口”，却都成为各自工作流里的默认选项。

    关键选择：工具数量与业务风险成反比。越涉及权限与生产数据，越要把“只读”“可撤销”做成一等公民。
    CASE 06 · 中国实践

    注册中心 + 网关，把存量接口“零改造”接入

    Nacos 3.0.1（2025-05-26）首个实现标准 MCP Registry API，并用 MCP-Router 把 stdio/SSE 代理为 Streamable HTTP；3.1 又加了 A2A 注册。Higress 2.1.5（2025-07-03）支持 OpenAPI→MCP、数据库→MCP 自动转换。百炼的“一键 MCP”免去逐服务器配置密钥，每个 Agent 最多挂 5 个服务，密钥由 KMS 托管。

    结果：高德 2025-03 上线 12 项 LBS 能力，ModelScope 2025-04 开出中文 MCP 社区。MCP 在内部更像“服务治理的延伸”，而不是新协议。

    关键选择：复用既有治理体系（注册中心、网关、KMS），而不是另起一套。接入成本低，才有人愿意发布工具。

    四个共同点

    ① 小工具面：3–15 个工具，命名可预测；② 输出可控：返回结构化、可裁剪、带游标的结果，而不是整库转储；③ 托管与鉴权到位：远程部署 + OAuth/作用域密钥，而不是本地明文 token；④ 场景窄：只做一件事，但在那件事上不需要说明书。这四点与“协议是否先进”几乎无关。

    07 / WHAT BREAKS

    失败样例：六个案例，一个根因从 55K tokens 的上下文爆炸，到一条 issue 偷走私库——它们坏在不同的地方，坏在同一个前提。

    FAIL 01 · COST

    GitHub MCP：93 个工具，55K tokens

    2025 年 8 月 23 日，Geoffrey Huntley 估算：在约 176K 可用上下文中，GitHub 一个服务器（93 个工具）占去约 55K，而大多数任务只会用到其中两三个。

    根因：tools/list 的“全有或全无”语义 + 客户端默认全量注入。服务器本身没有错。

    后续：GitHub 引入 toolsets 分组；2026-08 复测为 85 工具 26.6K、默认 44 工具 14.2K——数字好了一倍，但“一个服务器吃掉 7% 窗口”依然昂贵。Cursor 甚至设了 40 个工具的硬上限，第 41 个工具对模型直接不可见。
    FAIL 02 · SECURITY

    一条 issue，偷走私有仓库

    2025 年 5 月 26 日，Invariant Labs 演示：攻击者在公开 issue 中埋入指令，Claude 4 Opus 读取后调用 GitHub MCP 读取私有仓库，并开了一个公开 PR，把薪资与搬迁补贴数据泄露出去。

    根因：致命三要素同时成立——访问私有数据、处理不可信内容、具备对外发送能力。三者缺一，攻击不成立。

    教训：工具权限应按“最小可用”切分，出站网络必须白名单。
    FAIL 03 · TENANCY

    Asana MCP：跨租户数据泄漏

    2025 年 6 月 18 日披露：Asana 的 MCP 服务器 5 月 1 日上线，租户隔离检查发生在缓存之后，导致约 1,000 个组织互相看到项目名、任务与元数据。无需攻击者，正常使用就会触发。

    根因：单一多租户凭据 + 缓存后才校验归属（confused deputy），MCP 层假设“上游 OAuth 已经校验过”。

    教训：MCP 服务器是独立的安全边界，必须自己做对象级授权，不能继承“调用方应该已经校验过”。
    FAIL 04 · PRIVILEGE

    Supabase MCP：一句话拿到 service_role

    2025 年 7 月 8 日，General Analysis 演示：支持工单里埋入指令，Cursor 调用 Supabase MCP 查询 integration_tokens，把 OAuth 密钥写回攻击者可见的工单。

    根因：工具默认持有绕过行级安全的高权限密钥，且没有只读模式、没有查询白名单。

    教训：默认只读、按需提权、密钥不落盘——这三条比任何提示词防护都可靠。
    FAIL 05 · SUPPLY CHAIN

    Postmark MCP：一个 npm 包，带走所有邮件

    2025 年 9 月 25 日：仿冒的 postmark-mcp 包用 15 个正常版本建立信任，第 16 版（1.0.16）开始把每封经手邮件密送（BCC）到外部服务器。

    根因：stdio 型服务器以用户身份运行任意代码，安装即执行；生态缺少签名与沙箱。

    教训：npx -y 是供应链攻击的完美入口。企业应只允许签名镜像与容器化运行。
    FAIL 06 · MUTABLE TRUST

    Deadbugz：描述在运行时被换掉

    2026 年 9 月，云安全联盟披露一类“运行时门控的元数据投毒”：工具描述在审批时是良性的，在真正调用时按条件切换为恶意指令，静态扫描与人工审批全部失效。

    根因：信任对象是可变的。审批针对的是快照，执行用的是实时值。

    教训：清单必须签名 + 固定摘要（digest），运行时校验“描述未变”；变更即重新审批。

    不是个案，而是结构

    一项覆盖 21,643 个服务器、72,606 个版本的 registry 研究发现：51.1% 的多版本服务器修改过自述元数据，其中 40.6% 是静默修改，4.2% 在保持注册身份不变的情况下把远程端点指向了别处；另有 9.57% 存在未认证暴露。信任一旦建立在“第一次看到的样子”上，此后每一次热更新都是一次未经审批的部署。

    把六个案例抽象一下：五个失败原型

    原型典型症状根因对应解法
    全量暴露上下文在对话开始前就被吃满；模型选错工具目录与详情未分离，客户端只能全量注入检索式加载 + 服务端分层 + 延迟加载
    结果无界一次调用返回 200KB；第 10 轮还在为重放付费工具没有“结果预算”概念，默认原样回传分页游标 + 句柄 + 聚合摘要 + 紧凑编码
    信任可变审批时人畜无害，执行时暗藏指令描述与实现可热更新，审批基于快照签名清单 + 摘要固定 + 变更重审
    权限过大一个只读任务却握着管理员密钥凭据粒度粗，缺少只读模式与对象级授权最小权限 + 按需提权 + 行级/对象级校验
    出站失控数据被“正常工具调用”带出边界没有网络白名单，工具可访问任意域名沙箱出站策略 + 数据分级 + 人工确认

    一个被反复验证的结论

    安全事件几乎都不是“协议漏洞”，而是部署方式的问题：默认开启了不需要的能力、默认授予了不需要的权限、默认信任了不该信任的内容。这和 token 浪费的根因惊人地一致——都是“默认全给”。

    08 / OPTIONS

    六条可行路线，和它们各自的代价没有一条是免费的。下面每一项都标注了“省哪类成本”与“把风险搬到了哪里”。

    把设计空间摊开，能走的路只有六条。五条已在生产环境被验证，第六条（重造协议）在理论上最优，在工程上最差。

    A

    检索式加载

    生产可用不改服务器

    目录与详情分离：上下文里只放一个轻量检索工具和工具名摘要，模型按需检索，命中的 top-k 才展开完整 schema。Anthropic 用 defer_loading 把延迟加载的工具从初始 prompt 中彻底移除，因此不破坏缓存。

    收益
    定义 token −85%（72K→8.7K）；准确率反升 25pp。Claude Code 已默认开启，每次最多加载 5 个。
    代价
    多一次检索往返（187 工具实测 0.6–1.1s）；召回失败会直接导致任务失败；索引需随工具变更更新。
    适用
    工具数 >10、定义 >10K tokens。几乎零门槛，应作为默认基线。
    B

    代码模式

    生产可用收益最大

    只暴露一个 execute 工具，模型写代码在沙箱里调用类型化绑定。循环、条件、并行、聚合都在沙箱内完成，只有最终结果回到上下文。Cloudflare 用 isolate，Anthropic 用 code execution，FastMCP 把它做成服务器变换。

    收益
    定义降到 1K 级；中间结果 200KB→1KB；20 次工具调用省去 19 次推理往返。
    代价
    需要强隔离沙箱与出站管控；代码生成会出错；可观测性显著变差（你看到的是代码，不是意图）；权限模型要重画。
    适用
    API 面广、数据密集、多步编排。不适合单次简单查询。
    C

    网关门控

    企业主流客户端零改动

    在客户端与服务器之间放一个中间件：按用户意图、权限范围、会话状态筛选出 top-k 工具，只把这几份 schema 注入上下文。Tool Attention 进一步引入两阶段加载——常驻摘要池，命中后才取完整 schema。

    收益
    每轮 47.3K→2.4K（模拟）；GatewayBench 显示分层网关在工具数增长时成本保持平坦，而“全量摊平”的网关线性上涨；顺带统一鉴权、审计、配额。
    代价
    单点故障；多租户权限模型复杂；增加 10–50ms；召回质量就是系统上限。
    适用
    企业内数十个服务器、需要统一治理与计费。中国实践多走这条路。
    D

    输出整形

    立即可用零协议改动

    不动定义，只动结果：表格型数据换紧凑编码，大结果转句柄按需切片，超长列表分页，聚合在服务端完成再回传。它是唯一可以在一天内上线、且不需要动客户端的方案。

    收益
    结果 token −18%（独立评测）~ −40%（厂商口径）；对日志、报表、检索类工具效果最好。
    代价
    独立评测显示紧凑编码带来约 −9pp 准确率损失；解析失败会级联；压缩不可逆。
    适用
    结果体积远大于定义体积的场景。必须用任务成功率验收，不能只看 token。
    E

    CLI 优先

    被低估反协议

    不封装 MCP，直接把能力做成命令行工具。模型对 gh、git、curl 的先验知识就是“免费的工具定义”，--help 则是按需文档。

    收益
    定义成本 ≈0；固定 git 任务的对照实验中，纯 CLI 方案的综合成本比 MCP 低 5–28 倍，且 MCP 运行中有 12.9% 的花费没有换来任何完成的工作（CLI 为 2.2%）；组合与调试体验最好。
    代价
    无结构化错误；shell 权限过大；跨平台与沙箱适配差；非编码场景（设计、支付）不适用。
    适用
    编码 Agent、内部运维工具、已有成熟 CLI 的能力。MCP 之前先问一句：能不能做成 CLI？
    F

    从零设计新协议

    理论最优不建议

    重新定义 IDL、编码、能力寻址与调用语义，把“按需、预算、可缓存”写进协议本身。技术上完全可行，经济上几乎不可行。

    收益
    可以做到理论最优的上下文开销；不受历史包袱约束。
    代价
    生态冷启动；所有客户端与服务器重写；而 token 瓶颈根本不在 wire format；还要面对治理与标准化。
    适用
    仅在“客户端与服务器都自研、规模足够大、且需要长期差异化”的封闭生态中考虑。若必须做，只补两个空白：结果预算与句柄引用——discover 与 ttl 已由 2026-07-28 覆盖。

    组合，而不是选择

    生产系统的最优解通常是 A + C + D 作为基线（检索、门控、整形），B 作为高价值路径的加速器，E 作为兜底与降级方案。F 只在封闭生态里成立。下一节列出八条看似可行、实则走不通的路。

    09 / DEAD ENDS

    八条看起来很美、实则走不通的路每一条都有人试过，每一条都在某个环节把成本转移而不是消除。

    判断一条路线是否可行，只需问三个问题：它消除了哪一类 token？把风险转移到了哪里？转移后的风险是否更贵？

    01

    把上下文窗口扩到 1M，问题就解决了 最常见

    窗口变大不会让注意力变准。注入的无关工具与历史结果同比增加，信噪比下降；成本按时长线性上涨，长任务的二次成本被放大得更厉害。业界观察到的“70% 利用率后推理质量下滑”，不会因为窗口变大而消失。

    例外单次离线分析、无需多轮交互、且结果不需要复用。
    02

    把 schema 缩写成“天书”，用缩写换 token

    命名从 create_pull_request 缩成 cpr，能省 20% 不到；但模型正是靠名字与描述区分相似工具。省下的定义 token，会在“选错—重试—澄清”里加倍还回去。

    例外工具集极小、且配有高质量示例（Tool Use Examples 曾把参数准确率从 72% 拉到 90%）。
    03

    全量预加载，然后指望 prompt cache 兜底

    缓存只在“前缀完全一致”时命中。工具集一变、顺序一抖、租户一换，缓存立刻失效，而你还付着全量定义的窗口占用。多租户 SaaS 场景下，命中率通常远低于预期。

    例外单租户、工具集长期稳定、会话短而高频。即便如此，也应配合稳定排序（2026-07-28 已把它写进规范）。
    04

    造一个“万能 MCP”，聚合所有内部 API

    定义爆炸没有消失，只是从 N 个服务器转移到了 1 个服务器；还额外获得单点故障、权限混乱、版本耦合。把“聚合”当成“暴露”，是最典型的偷懒。GatewayBench 在 7 个网关、11,118 个工具上测过：全量摊平的网关，token 与时延随工具数线性增长，间接攻击成功率 60.5%；分层网关则保持平坦，攻击成功率 19.6%。

    例外聚合层只做检索与路由，不把全部 schema 注入上下文——这正是路线 C 的做法。
    05

    用另一个 LLM 给每次工具结果做摘要

    成本与延迟翻倍；摘要在信息损失上不可控；错误会沿着链条传播且难以审计。对高频调用，这是最贵的“省 token”方式。

    例外超大文档的离线预处理，一次生成、多次复用，且保留原文句柄可回溯。
    06

    换成 Protobuf / CBOR / 二进制传输来省 token

    tokenizer 看到的是文本。二进制能省带宽、省解析时间，但省不了提示词里的 token——除非你在客户端把它重新渲染成文本，那就回到了原点。调试成本还显著上升。

    例外大文件、流式数据、非提示词路径的传输通道。
    07

    用多 Agent 扇出来规避单个上下文过载

    每个子 Agent 都要重新装载工具定义与任务背景，成本线性甚至超线性上升；协调、汇总、冲突消解又引入新的 token 开销。它适合“可并行的独立子任务”，不适合“绕开上下文限制”。

    例外子任务彼此独立、可并行、且结果可结构化汇总（如批量审查、多源检索）。
    08

    微调模型，让它“记住”工具；或依赖 server 反向调用模型

    工具版本一升级，微调成果立刻过期；供应商锁定严重。至于 sampling（服务器反向请求客户端模型），2026-07-28 规范已将其列入弃用——它把成本与安全边界都推给了不可控的一方。

    例外领域 API 极其稳定、且你有能力持续重训的封闭场景。

    一条简单的判据

    任何“省 token”的方案，如果没有减少进入模型的信息量，只是把它换了个地方存放，那它迟早会以另一种成本回来——通常是延迟、准确率或安全面。

    三条决策规则

    RULE 01

    你控制哪一端？

    只控制服务器 → 走 A + D（检索由客户端做，你只需让输出可裁剪）；只控制客户端 → 走 A + B；两端都不控制 → 走 C。

    RULE 02

    任务是编码型还是数据型？

    编码型优先 E（CLI + Skills），MCP 只保留有状态交互；数据型优先 B（代码模式），因为中间结果不该进上下文。

    RULE 03

    合规压力有多大？

    强监管/多租户 → C 是唯一能统一审计与配额的形态；弱监管/单团队 → A + D 两周即可上线。

    11 / PROPOSAL

    如果要做，就做“剖面 + 运行时”，而不是新协议一个 MCP 兼容的上下文平面：南向不改服务器，北向只给模型四个工具。

    我们把这个方案叫作 LCP（Layered Context Profile，分层上下文剖面）。它不是一套新的线上协议，而是三层约定加一个运行时：剖面规定“模型应该看到什么”，运行时负责“怎么看到”。

    六个组件，各自只做一件事

    组件职责关键设计失效模式
    Manifest Store缓存每个服务器的能力卡片与摘要，替代全量 schema签名 + digest + TTL；变更即失效；按需展开详情缓存陈旧 → 调用不存在的工具
    Retriever把用户意图映射到 top-k 工具BM25 与向量混合；叠加权限与状态过滤；低置信度返回空漏召回 → 任务直接失败
    Budgeter分配每轮、每结果、每任务的 token 配额超限自动转句柄或分页，而不是截断配额过紧 → 信息不足
    Executor在沙箱内执行模型生成的代码，调用类型化绑定默认无网络；出站白名单；CPU/内存/时长限额沙箱逃逸 / 资源耗尽
    Shaper把原始结果转换为模型友好的形态表格用紧凑编码；大对象转句柄；保留可回溯原文压缩过度 → 准确率下降
    Policy & Audit鉴权、审批、配额、全链路追踪每次调用记录 who/what/why；高危操作强制人工确认审计缺失 → 无法定责

    服务侧的五条硬规则

    协议只能约束“怎么调”，约束不了“长什么样”。如果你在写服务器，这五条比任何协议优化都有效：

    • 工具 ≤ 15 个：超过就拆服务器，或用 toolsets 分组。工具数量是唯一能被用户直接感知的成本。
    • 一屏读完：全部工具名 + 一行描述控制在 400 tokens 以内；超出的信息放到 inspect 或文档里。
    • 描述写“何时用”，而不是“是什么”；相似工具必须写明差异，否则模型一定会选错。
    • 结果永远可分页：返回游标、给默认 limit、禁止无界列表。一次返回 10 万行是设计缺陷，不是能力。
    • 默认只读：写操作单独授权；危险操作要求确认、幂等键与可回滚路径。

    三份契约，把“省 token”变成可执行的接口

    协议的价值不在于定义字段，而在于定义双方都必须遵守的约束。LCP 只新增三份契约，全部可作为 MCP 扩展实现。

    CONTRACT 01 · MANIFEST（单工具约 35 tokens）

    {
  "id": "github", "v": "2.1.0", "digest": "sha256:9f2c…", "ttl": 3600,
  "tags": ["scm", "issues", "ci"],
  "tools": [
    { "n": "create_pr",  "sig": "repo*,head*,base*,title?,body?", "when": "需要新建 PR" },
    { "n": "list_issues", "sig": "repo*,state?,label?",     "when": "按状态筛选 issue" }
  ]
}

    对比：GitHub 全量 85 个工具的 schema 约 26,600 tokens（2025 年同口径为 93 个 / 55,000）。清单只保留“名字 + 签名 + 何时用”，完整 schema 在 inspect_tool 时才展开。签名里的 * 表示必填，? 表示可选——一个字符替代一段 JSON Schema。

    CONTRACT 02 · BUDGET（每次调用都带配额）

    run({
  code: "...",
  budget: {
    max_result_tokens: 1200,      // 超出即转句柄，不截断
    format: "toon",             // toon | md | json
    on_exceed: "handle",        // handle | paginate | error
    deadline_ms: 8000
  }
})

    “预算”必须由调用方声明、由执行方强制，而不是靠提示词提醒模型“少输出”。这是把软约束变成硬约束的关键一步。

    CONTRACT 03 · HANDLE（大结果只回引用）

    // 沙箱内：数据留在执行侧
const prs = await github.search_prs({ repo, state: "open" });
const stale = prs.filter(p => days(p.updatedAt) > 14);
return stale.map(p => ({ n: p.number, t: p.title }));   // 仅 20 行回上下文

// 需要细节时，按句柄分页取回
read_handle("h_8f2c", { cursor: 0, limit: 50 })

    为什么是“剖面”而不是“协议”

    ① 南向零改造：13,087 个可用端点直接复用，不需要说服任何人重写服务器；② 北向极简：四个工具长期稳定，prompt 前缀不变，缓存命中率最大化；③ 可独立迭代：检索、预算、整形都在代理层，能 A/B、能回滚；④ 安全收敛：只要守住沙箱与出站两个边界，风险面远小于“给每个服务器发一把钥匙”。

    与 2026-07-28 规范对齐，而不是对抗

    • server/discover 正好是“先目录、后详情”的协议依据：一次探测拿到版本、能力与指令，替代分别拉取三个 list。
    • ttlMs / cacheScope 让清单可以合法缓存；稳定排序让北向前缀稳定，直接提升 prompt cache 命中。
    • 无状态请求让代理层可以水平扩展、随意重试，不必为“保住会话”而保住上下文。
    • extensions 字段让 manifest / budget / handle 可以作为官方扩展存在，而不是私货。

    13 / RECOMMENDATION

    八条建议，按可执行性排序如果只能记住一句话：把“工具”当成接口设计问题，而不是提示词问题。

  • 不要造协议，造剖面

    MCP 的网络效应已经形成：36,134 条 registry 条目、97M+ 月 SDK 下载、所有主流客户端。新协议的收益上限是“省一点编码”，成本下限是“从零赢一遍生态”。把创新放在运行时与剖面层，收益/成本比高一个数量级。

  • 先量后调，没有基线的优化都是猜测

    至少采集四个数：每轮定义 token、每结果 token、工具选择准确率、单任务成本（含重试）。很多团队以为自己在优化定义税，实际最大的开销在结果重放。

  • 先治结果，再治定义

    定义税线性、可缓存；结果税二次、会复利。以 55K 定义、20 轮、每轮 10K 结果计，结果累计 2.1M，是定义税的近两倍；单次 50K 时是 9.5 倍。优先级：句柄 > 分页 > 聚合 > 编码压缩。

  • 客户端可控就上代码模式，否则上网关

    能改客户端（自研 Agent、内部平台）→ 直接做 execute 沙箱，收益最大；只能改服务器 → 做检索与输出整形；两端都不控 → 在企业边界部署网关。

  • 把“预算”写进接口，而不是写进提示词

    “请只返回摘要”是一句请求，不是约束。真正的约束是 max_result_tokens + on_exceed: handle，由执行方强制执行。软约束会被模型忽略，硬约束不会。

  • 稳定性优先于压缩率

    一份更短但每轮都变的目录，可能比一份更长但完全命中的目录更贵。保持工具顺序稳定、清单可缓存、前缀不变——这是 2026 年协议层给出的最重要信号。

  • 安全边界画在沙箱与出站，不要画在提示词

    提示词注入无法被“更强的系统提示”根治。有效的手段只有三个：最小权限、出站白名单、高危操作人工确认。工具描述还要签名并固定 digest，防止运行时被替换。

  • 向上游提案，不要 fork

    manifest / budget / handle 都可以做成 MCP 扩展（extensions 字段已就位）。提交 SEP、开源参考实现、先在内部跑通，比另起炉灶更容易获得长期回报。

    • MCP 把“连接”变成了商品，于是价值必然上移到“选择与编排”。下一个工具协议的机会，不在插座的形状，而在决定“此刻该让模型看见什么”的那一层。 — 结论

    如果只做一件事

    给你的 Agent 加一个 “工具预算器”：每轮声明工具定义上限，每个结果声明 token 上限，超限转句柄。这一个改动通常能在两周内把账单砍掉一半，且不需要改协议、不需要换客户端。
